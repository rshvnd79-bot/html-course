۰

سند، زبان و متادیتا — ریزترین نکات

در این درس اسکلت یک سند HTML را از DOCTYPE تا head و body می‌سازیم و دقیق می‌بینیم هر بخش چه مسئولیتی دارد.

۱. مفهوم را دقیق بفهم

یک سند HTML فقط مجموعه‌ای از تگ‌ها نیست؛ مرورگر ابتدا سند را parse می‌کند، ساختار DOM را می‌سازد و سپس metadata و محتوای body را برای نمایش و رفتار صفحه به‌کار می‌گیرد. DOCTYPE حالت استاندارد را فعال می‌کند؛ عنصر html ریشه سند است؛ lang زبان محتوای غالب را مشخص می‌کند؛ dir جهت نوشتار را تعیین می‌کند؛ head محل metadata و وابستگی‌های سند است؛ و body محتوای قابل‌مشاهده و تعامل صفحه را در خود دارد.

چرا مهم است؟

اگر این لایه را درست نسازی، خطاهای بعدی مثل کدگذاری اشتباه فارسی، رفتار نامناسب متن دوزبانه، عنوان نامناسب تب مرورگر، ریسپانسیو نبودن صفحه یا metadata ناقص ممکن است از همان ابتدا وارد پروژه شوند.

۲. ریزه‌کاری‌های این کورس

  • DOCTYPE — <!doctype html> نسخه HTML را انتخاب نمی‌کند؛ یک declaration کوتاه است که مرورگر را به standards mode می‌برد. در HTML مدرن همین فرم ساده را استفاده کن.
  • html + lang + dir — <html lang="fa" dir="rtl"> ریشه سند است. lang باید با یک language tag معتبر BCP 47 زبان محتوای غالب را توصیف کند. برای بخش‌های انگلیسی یا LTR می‌توان روی همان بخش lang="en" و در صورت نیاز dir="ltr" گذاشت.
  • head — head مجموعه‌ای از metadata است، نه محلی برای محتوای قابل‌مشاهده. title ، meta ، link ، style و script های مرتبط با سند از مهم‌ترین اعضای آن هستند.
  • charset — <meta charset="utf-8"> کدگذاری سند را اعلام می‌کند. برای اسناد HTML معمولی UTF-8 انتخاب استاندارد و عملی است و بهتر است declaration خیلی زود در سند قرار بگیرد.
  • viewport — الگوی معمول <meta name="viewport" content="width=device-width, initial-scale=1"> به مرورگرهای موبایل می‌گوید viewport را با عرض دستگاه هماهنگ کنند. برای دسترس‌پذیری، زوم کاربر را بی‌دلیل محدود نکن.
  • title و description — title عنوان سند را تعیین می‌کند و در تب مرورگر و نقاط مختلف رابط کاربری استفاده می‌شود. meta description metadata توصیفی صفحه است؛ محتوای دقیق و منحصربه‌فرد بهتر از متن تکراری است، اما تضمینی برای نمایش همان متن در نتایج جست‌وجو نیست.
  • link — link رابطه سند با منبع خارجی را تعریف می‌کند؛ stylesheet، icon و canonical نمونه‌های رایج‌اند. canonical یک راهنمای URL ترجیحی برای موتورهای جست‌وجو است، نه ریدایرکت.
  • body — body محتوای document body را نگه می‌دارد؛ چیزهایی که کاربر در صفحه می‌بیند یا با آن‌ها تعامل می‌کند عمدتاً از اینجا می‌آیند.

۳. مثال کامل قابل اجرا

این مثال را می‌توانی مستقیم در یک فایل HTML قرار بدهی و نتیجه را در مرورگر ببینی. 

<!doctype html>
<html lang="fa" dir="rtl">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>نمونه‌کار من</title>
    <meta name="description" content="معرفی نمونه‌کارهای یک توسعه‌دهنده وب.">
  </head>
  <body>
    <main>
      <h1>نمونه‌کار من</h1>
      <p>به صفحه شخصی من خوش آمدید.</p>
    </main>
  </body>
</html>

۴. اشتباهات رایج

  • استفاده از lang="fa" فقط به خاطر فارسی بودن یک جمله، در حالی که زبان غالب سند چیز دیگری است.
  • قرار دادن متن قابل‌مشاهده داخل head به جای body .
  • استفاده از meta name="viewport" با user-scalable=no یا محدودیت‌های غیرضروری زوم.
  • اشتباه گرفتن title با <h1> ؛ اولی metadata سند است و دومی heading محتوای صفحه.
  • قرار دادن URL ساختگی برای canonical بدون اینکه واقعاً URL ترجیحی پروژه باشد.

۵. نکات طلایی حرفه‌ای

  • UTF-8 را در سندهای فارسی انتخاب کن و declaration آن را زود قرار بده.
  • lang را روی ریشه سند تنظیم کن و برای بخش‌های واقعاً متفاوت، زبان را محلی override کن.
  • برای جهت نوشتار از dir استفاده کن؛ برای متن دوزبانه به bidi و dir="auto" هم توجه داشته باش.
  • viewport برای موبایل مهم است، اما ریسپانسیو شدن واقعی فقط با meta viewport اتفاق نمی‌افتد؛ CSS هم لازم است.
  • metadata را برای هر صفحه متناسب با همان صفحه بنویس؛ کپی کردن title و description بین همه صفحات کیفیت اطلاعات سند را پایین می‌آورد.
  • head و header دو چیز متفاوت‌اند: head metadata سند است، header محتوای مقدماتی یک صفحه یا بخش است.

۶. تمرین

یک صفحه فارسی بساز که عنوان، description، favicon، canonical، lang، dir، charset و viewport را داشته باشد. سپس یک پاراگراف انگلیسی داخل آن قرار بده و زبان آن بخش را به‌درستی مشخص کن.

فلش‌کارت — ریزنکات این بخش

DOCTYPE امروز چه نقشی دارد؟ یک سوییچ، نه یک نسخه
  • node ۱: <!DOCTYPE html> دیگر نسخهٔ HTML را اعلام نمی‌کند؛ فقط مرورگر را به «حالت استاندارد» می‌برد.
  • بدون آن، مرورگر ممکن است وارد «quirks mode» شود و برخی رفتارهای تاریخی، از جمله تفاوت‌های مدل جعبه، فعال شوند.
  • برای آموزش دقیق‌تر، تفاوت مدل جعبه را به‌صورت تاریخی بررسی کن؛ این رفتار برای همهٔ عناصر و همهٔ شرایط یکسان نیست.
  • پس هر اختلاف ظاهری عجیب در مرورگرهای قدیمی را اول با نبود DOCTYPE بررسی کن.
مقادیر مجاز lang چه هستند؟ از BCP 47 استفاده کن
  • زبان با کد زبان و در صورت نیاز کد منطقه نوشته می‌شود: fa ، fa-IR ، en-US .
  • fa-IR زبان فارسی با منطقهٔ ایران را دقیق‌تر توصیف می‌کند؛ اینکه تلفظ چگونه انجام شود به مرورگر، سیستم‌عامل و موتور تبدیل متن به گفتار بستگی دارد.
  • برای بخش لاتین داخل صفحه فارسی، lang="en" را روی همان عنصر بگذار.
  • attr q: تفاوت lang و xml:lang — در HTML5 فقط lang لازم است.

۱. مفهوم را دقیق بفهم

HTML متن را به لایه‌های معنایی تقسیم می‌کند. headingها ساختار را می‌سازند؛ strong و em معنا و اهمیت/تأکید را بیان می‌کنند؛ b و i برای نقش‌های متنی خاصی هستند و صرفاً «تگ‌های CSS» نیستند؛ mark برجسته‌سازی مرتبط با زمینه است؛ small برای حاشیه‌ها و توضیحات کوچک‌تر؛ code و pre برای نمایش کد؛ blockquote و q برای نقل‌قول؛ time برای زمان ماشین‌خوان؛ del و ins برای تغییرات؛ و ruby برای annotationهای نوشتاری.

چرا مهم است؟

معنای درست متن به مرورگر، فناوری کمکی و ابزارهای پردازش محتوا کمک می‌کند. CSS باید ظاهر را کنترل کند، نه اینکه با div و span معنی heading، نقل‌قول یا اهمیت متن را شبیه‌سازی کند.

۲. ریزه‌کاری‌های این کورس

  • Headingها — h1 تا h6 سطح heading را مشخص می‌کنند. سطح‌ها را بر اساس ساختار محتوا انتخاب کن، نه اندازه فونت. اندازه و فاصله با CSS تعیین می‌شود.
  • strong و em — strong اهمیت یا seriousness بیشتری را منتقل می‌کند؛ em تأکید است و تغییر emphasis جمله را نشان می‌دهد. نحوه اعلام این معنا توسط screen reader می‌تواند متفاوت باشد و نباید به یک صدای خاص وابسته شوی.
  • b و i — b برای جلب توجه بدون انتقال importance ویژه مناسب است؛ i برای صدای متفاوت، اصطلاح فنی، اصطلاح خارجی و موارد مشابه کاربرد دارد. اگر فقط رنگ یا وزن می‌خواهی، CSS استفاده کن.
  • mark و small — mark بخش مرتبط یا برجسته در context فعلی را نشان می‌دهد؛ search highlight یکی از کاربردهای رایج است. small برای side comments، copyright و متن‌های فرعی مناسب است.
  • blockquote/q/cite — blockquote برای نقل‌قول بلوکی و q برای نقل‌قول درون‌خطی است. attribute cite می‌تواند URL منبع را بدهد؛ عنصر <cite> معمولاً عنوان یک اثر را نشان می‌دهد، نه صرفاً نام نویسنده.
  • code/pre/kbd/samp — code قطعه کد را مشخص می‌کند، pre فاصله‌گذاری و line breaks را حفظ می‌کند، kbd ورودی کاربر و samp نمونه خروجی برنامه را نشان می‌دهد.
  • del/ins و time — del حذف و ins افزوده شدن را مشخص می‌کنند و می‌توانند datetime داشته باشند. time datetime نمایش انسانی را از مقدار machine-readable جدا می‌کند.
  • sub/sup و ruby — sub/sup برای زیرنویس و بالانویس معنایی مثل فرمول یا پاورقی کوتاه هستند؛ برای صرفاً کوچک‌کردن متن مناسب نیستند. ruby برای annotation تلفظی/توضیحی در نوشتارهایی که از آن پشتیبانی می‌کنند به‌کار می‌رود.

۴. اشتباهات رایج

  • استفاده از h1 تا h6 فقط برای بزرگ و کوچک کردن متن.
  • استفاده از strong/em وقتی تنها هدف تغییر ضخامت یا ایتالیک بودن است.
  • فرض اینکه b و i کاملاً بی‌معنا هستند.
  • قرار دادن نام نویسنده داخل cite و تصور اینکه خود عنصر cite یعنی «نویسنده».
  • استفاده از placeholderهای تصویری مثل _____ به جای ساختار معنایی مناسب.

۵. نکات طلایی حرفه‌ای

  • ساختار heading را قبل از طراحی CSS مشخص کن.
  • برای ظاهر صرف از CSS استفاده کن؛ برای معنی از HTML.
  • برای متن‌های دوزبانه lang و در صورت نیاز dir را روی بخش مربوط تنظیم کن.
  • برای زمان‌هایی که باید توسط ماشین فهمیده شوند، datetime را جدی بگیر.
  • blockquote و q را برای نقل‌قول واقعی نگه دار، نه برای indentation بصری.
  • در code نمونه‌های کوتاه را با code و بلوک‌های چندخطی را با pre+code نمایش بده.

strong و b واقعاً چه تفاوتی دارند؟ معنا در برابر ظاهر

  • b برای جلب توجه بدون انتقال اهمیت ویژه به‌کار می‌رود؛ اگر صرفاً ظاهر می‌خواهی، CSS انتخاب بهتری است.
  • em تأکید در جمله است و لحن را عوض می‌کند: «من این را نگفتم».
  • i برای اصطلاح بیگانه یا فنی است، مثل نام لاتین یک گونه.
del و ins چه زمانی درست پیاده می‌شوند؟ تغییرات نسخه‌ای
  • del متن حذف‌شده و ins متن افزوده‌شده را نشان می‌دهند.
  • هر دو datetime و cite می‌پذیرند تا زمان و منبع تغییر ثبت شود.
  • در متن حقوقی یا نسخهٔ سند، این دو با رنگ و خط‌خوردگی معنا را می‌رسانند.
  • به‌جای دوتایی‌کردن متن با رنگ، از همین تگ‌ها استفاده کن.
blockquote و q چه فرقی دارند؟ بلوکی در برابر درون‌خطی
  • blockquote نقل‌قول بلوکی است و معمولاً تودرتویی/تورفتگی می‌گیرد.
  • q نقل‌قول کوتاه درون‌خطی است و مرورگر خودش گیومه اضافه می‌کند.
  • منبع نقل‌قول را در cite بگذار؛ خودِ عنصر cite باید نام اثر باشد، نه آدرس.
  • اگر فقط متن کج و گیومه می‌خواهی، متن سادهٔ داخل p کافی است.
time، abbr و dfn را چرا بنویسیم؟ قابل فهم برای ماشین و انسان
  • time datetime="2024-05-01" تاریخ خوانا برای ماشین می‌سازد.
  • abbr title="HyperText Markup Language" مخفف را برای صفحه‌خوان باز می‌کند.
  • dfn جای تعریف اصطلاح است و با اولین کاربرد آن می‌آید.
  • این‌ها به سئو و دسترس‌پذیری همزمان کمک می‌کنند.
sub، sup، wbr و br کجا؟ کنترل دقیق متن
  • sub پایین‌نویس (H₂O) و sup بالانویس (۲³) است.
  • wbr نقطهٔ شکست اختیاری در کلمات بلند است، مثل example domain.com .
  • br فقط شکست خط در متن‌هایی مثل آدرس یا شعر است، نه برای فاصلهٔ چیدمانی.

فهرست‌ها: ul، ol، dl و menu

فهرست‌ها را بر اساس نوع رابطه داده‌ها انتخاب می‌کنیم: مجموعه، ترتیب، یا جفت اصطلاح/توضیح.

خروجی یادگیری فهرست‌ها: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
تمرین کوتاه منوی ناوبری، فهرست مراحل و یک واژه‌نامهٔ کوتاه بساز و نوع فهرست هرکدام را توضیح بده.
قاعدهٔ طلایی برای ناوبری از nav + ul شروع کن.
📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

۱. مفهوم را دقیق بفهم

ul برای مجموعه‌ای است که ترتیب آیتم‌ها در معنای محتوا مهم نیست؛ ol برای ترتیب مهم؛ dl برای گروه‌هایی از term و description؛ و menu برای فهرست commandها/آیتم‌های تعاملی در معنای HTML. برای navigation عمومی، معمولاً nav به همراه ul/ol مناسب‌تر از menu است.

چرا مهم است؟

فهرست معنایی هم ساختار را خواناتر می‌کند و هم اجازه می‌دهد مرورگر و فناوری کمکی رابطه آیتم‌ها را بفهمند. ساختن list با div و CSS فقط ظاهر را تقلید می‌کند.

۲. ریزه‌کاری‌های این کورس

  • ul — برای مجموعه‌هایی مثل ویژگی‌ها، دسته‌بندی‌ها یا آیتم‌های unordered استفاده می‌شود. نوع bullet با CSS کنترل می‌شود.
  • ol — وقتی ترتیب مهم است استفاده کن؛ start ، reversed و type برای سناریوهای مشخص وجود دارند. شماره‌گذاری را با CSS یا متن دستی تقلید نکن.
  • dl — برای term/description مناسب است؛ یک dt می‌تواند با چند dd یا چند dt برای یک توضیح مرتبط شود، بسته به مدل محتوای واقعی.
  • menu — در HTML مدرن فهرست commandها/آیتم‌های فرمانی است و جایگزین عمومی ul برای navigation نیست.
  • Nested lists — لیست تو در تو باید داخل li والد قرار بگیرد. این ساختار رابطه parent/child را روشن می‌کند.
  • Accessibility — متن آیتم را کامل نگه دار؛ برای نقش‌های interactive از button/a استفاده کن، نه li کلیک‌پذیر بدون semantics.

۳. مثال کامل قابل اجرا

این مثال را می‌توانی مستقیم در یک فایل HTML قرار بدهی و نتیجه را در مرورگر ببینی. 

<nav aria-label="فهرست اصلی">

    <li><a href="/">خانه</a></li>
    <li><a href="/projects">پروژه‌ها</a></li>
    <li><a href="/contact">تماس</a></li>

<dl>

  <dt>CSS</dt><dd>ارائه و layout</dd>
</dl>

۴. اشتباهات رایج

  • استفاده از menu به عنوان جایگزین همیشگی ul در navigation.
  • ساخت list با div و bullet دستی.
  • قرار دادن ol وقتی ترتیب هیچ معنایی ندارد.
  • قرار دادن nested list بیرون از li والد.
  • استفاده از dl صرفاً چون شبیه جدول دو ستونه است، بدون رابطه term/description واقعی.

۵. نکات طلایی حرفه‌ای

  • اول معنی رابطه را مشخص کن، بعد تگ را انتخاب کن.
  • اگر کاربر باید به صفحه‌ای برود، a است؛ اگر action انجام می‌دهد، button است.
  • شماره‌گذاری ol را با start/reversed/type وقتی معنا دارد کنترل کن.
  • برای navigation از nav به همراه ساختار list خوانا استفاده کن.
  • در mobile listها را با CSS خوانا نگه دار و line-height مناسب بده.

۶. تمرین

یک navigation سه‌سطحی بساز، سپس یک دستورالعمل مرحله‌ای با ol و یک واژه‌نامه کوچک با dl ایجاد کن. توضیح بده چرا هرکدام را انتخاب کردی.

    جدول‌ها: table، caption، thead، tbody، tfoot، colgroup

    جدول برای داده‌های رابطه‌ای است، نه برای layout. در این درس ساختار کامل و دسترس‌پذیر جدول را می‌سازیم.

    خروجی یادگیری جدول: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
    تمرین کوتاه جدول پروژه‌ها را با caption، سرستون‌های مشخص، scope و نسخهٔ قابل اسکرول در موبایل بساز.
    قاعدهٔ طلایی در موبایل جدول را مجبور به شکستن ستون‌هایش نکن.
    📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

    ۱. مفهوم را دقیق بفهم

    جدول از rows و cells تشکیل می‌شود و header cellها رابطه داده‌ها را تعریف می‌کنند. caption عنوان/توضیح جدول است؛ thead ، tbody و tfoot گروه‌بندی ساختاری ردیف‌ها هستند؛ th سرستون/سرگروه و td سلول داده است؛ scope یا headers می‌تواند ارتباط header و cell را دقیق‌تر کند؛ colgroup برای گروه‌بندی ستون‌هاست.

    چرا مهم است؟

    اگر جدول فقط با border و div ساخته شود، ظاهر ممکن است شبیه جدول باشد اما رابطه داده‌ها برای کاربر و فناوری کمکی مبهم می‌شود.

    ۲. ریزه‌کاری‌های این کورس

    • table/caption — table باید داده دو بعدی واقعی داشته باشد. caption باید کوتاه و معنادار باشد و context جدول را معرفی کند.
    • thead/tbody/tfoot — این‌ها بخش‌های ساختاری جدول‌اند. مرورگر ممکن است tbody را حتی اگر ننویسی به DOM اضافه کند؛ نوشتن ساختار واضح برای خوانایی کد مفید است.
    • th/td/scope — th header است. scope="col" یا scope="row" در جدول‌های معمولی ارتباط را روشن می‌کند. برای روابط پیچیده‌تر از headers / id استفاده می‌شود.
    • colgroup — برای گروه‌بندی ستون‌ها و برخی styling/metadataهای ستونی مناسب است؛ layout صفحه را با table حل نکن.
    • responsive tables — جدول ذاتاً ممکن است از عرض موبایل بزرگ‌تر شود. wrapper با overflow:auto یا الگوی تبدیل داده به کارت در breakpoint مناسب می‌تواند تجربه موبایل را بهتر کند.

    ۳. مثال کامل قابل اجرا

    این مثال را می‌توانی مستقیم در یک فایل HTML قرار بدهی و نتیجه را در مرورگر ببینی. 

    <div class="table-scroll">
<table>
  <caption>وضعیت پروژه‌ها</caption>
  <thead><tr><th scope="col">پروژه</th><th scope="col">وضعیت</th><th scope="col">درصد</th></tr></thead>
  <tbody><tr><th scope="row">فروشگاه</th><td>در حال توسعه</td><td>70%</td></tr><tr><th scope="row">وبلاگ</th><td>منتشر شده</td><td>100%</td></tr></tbody>
  <tfoot><tr><th scope="row">میانگین</th><td colspan="2">85%</td></tr></tfoot>
</table>

    ۴. اشتباهات رایج

    • استفاده از table برای چیدمان صفحه.
    • حذف caption و headerها چون جدول «واضح» به نظر می‌رسد.
    • استفاده از td برای header.
    • وابسته کردن معنا به رنگ یا border.
    • اجبار جدول به شکستن عجیب در موبایل به جای استفاده از overflow یا الگوی مناسب.

    ۵. نکات طلایی حرفه‌ای

    • هر جدول باید سؤال مشخصی را جواب بدهد.
    • برای row header هم th قابل استفاده است.
    • scope را در جدول‌های ساده به‌کار ببر.
    • در موبایل اول readability را حفظ کن، بعد فشرده‌سازی را دنبال کن.
    • برای داده‌های پیچیده‌تر، headers/id را بررسی کن.

    ۶. تمرین

    یک جدول قیمت‌گذاری سه‌ستونه با caption، thead، tbody، tfoot و scope بساز و آن را داخل wrapper افقی قرار بده تا در موبایل overflow کنترل‌شده داشته باشد.

    ناوبری و لینک‌ها: a، nav و همهٔ انواع href

    لینک‌ها ستون فقرات navigation وب هستند؛ در این درس هم خود a و هم انواع URL و رابطه‌های link را تفکیک می‌کنیم.

    خروجی یادگیری لینک‌ها: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
    تمرین کوتاه برای پرتفولیو لینک داخلی، خارجی، mailto، tel، دانلود و target مناسب بساز.
    قاعدهٔ طلایی متن لینک باید بدون خواندن اطرافش هم قابل فهم باشد.
    📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

    ۱. مفهوم را دقیق بفهم

    a با href یک hyperlink ایجاد می‌کند. مقصد می‌تواند URL نسبی، مطلق، fragment، mailto یا tel باشد. nav برای بخش‌های navigation است و rel در روابط خاص لینک معنا می‌دهد. target محل باز شدن را کنترل می‌کند اما نباید صرفاً برای همه لینک‌ها استفاده شود.

    چرا مهم است؟

    لینک درست باید هم مقصد درست داشته باشد، هم متن قابل‌فهم، هم رفتار امن و قابل پیش‌بینی. لینک «اینجا کلیک کنید» بدون context ضعیف‌تر از متن توصیفی است.

    ۲. ریزه‌کاری‌های این کورس

    • Absolute/relative — URL مطلق شامل scheme و host است؛ URL نسبی نسبت به document/base URL resolve می‌شود. slash ابتدایی یعنی مسیر نسبت به origin.
    • Fragment — href="#contact" به عنصری با id مشخص می‌پرد. id باید یکتا باشد.
    • mailto/tel — برای email و تماس تلفنی مناسب‌اند، اما روی دستگاه و نرم‌افزار کاربر وابسته به handler سیستم عمل می‌کنند.
    • nav — nav برای major navigation blocks است، نه هر گروه کوچک لینک. ممکن است چند nav با aria-labelهای متمایز داشته باشی.
    • rel/target — برای لینک‌های خارجی با target="_blank" ، رفتار opener را آگاهانه مدیریت کن؛ در مرورگرهای مدرن noopener در بسیاری از حالت‌ها پیش‌فرض شده اما نوشتن intent در کد می‌تواند واضح باشد. rel="nofollow" هم مفهوم متفاوتی دارد و نباید کورکورانه استفاده شود.
    • Download — attribute download برای پیشنهاد دانلود منابع same-origin یا شرایط مجاز مناسب است؛ تضمین نمی‌کند هر URL خارجی حتماً دانلود شود.

    ۴. اشتباهات رایج

    • استفاده از button برای navigation.
    • استفاده از div با click handler به جای a.
    • متن لینک مبهم مثل «اینجا» در فهرست‌های طولانی.
    • لینک کردن به id تکراری یا مقصدی که وجود ندارد.
    • باز کردن همه لینک‌ها در تب جدید بدون دلیل.

    ۵. نکات طلایی حرفه‌ای

    • متن لینک باید مقصد را حتی خارج از context اطراف توضیح دهد.
    • برای action از button و برای navigation از a استفاده کن.
    • fragmentها را برای پرش داخل همان document استفاده کن.
    • URLهای نسبی را نسبت به ساختار واقعی deployment خودت بررسی کن.
    • برای external links رفتار امنیتی و UX را آگاهانه انتخاب کن.

    ۶. تمرین

    یک nav کامل بساز که لینک داخلی، fragment، ایمیل، تلفن و لینک خارجی داشته باشد. برای هرکدام توضیح بده چرا نوع href متفاوت است.

    تصویر: img، srcset، picture، figure و عکس واکنش‌گرا

    تصویر فقط یک فایل نیست؛ باید منبع، اندازه، جایگزین متنی، انتخاب منبع و نسبت آن با layout را درست طراحی کنیم.

    خروجی یادگیری تصویر: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
    تمرین کوتاه یک تصویر قهرمان با width/height، alt و srcset بساز و برای دو برش هنری از picture استفاده کن.
    قاعدهٔ طلایی در موبایل و دسکتاپ تصویر را بدون پرش چیدمان نمایش بده.
    📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

    ۱. مفهوم را دقیق بفهم

    img برای تصویر است و alt متن جایگزین را مشخص می‌کند. width و height به مرورگر کمک می‌کنند فضای تصویر را از قبل رزرو کند. srcset و sizes برای انتخاب منابع مناسب بر اساس شرایط نمایش هستند. picture برای art direction یا انتخاب منبع بر اساس media/type مناسب است. figure و figcaption رابطه تصویر با caption را مشخص می‌کنند.

    چرا مهم است؟

    تصویر اشتباه می‌تواند صفحه را سنگین، CLS را زیاد، تجربه screen reader را مبهم و روی موبایل مصرف داده را بالا ببرد.

    ۲. ریزه‌کاری‌های این کورس

    • alt — برای تصویر informative یک توصیف کوتاه و هدفمند بنویس. تصویر decorative معمولاً alt="" دارد تا فناوری کمکی آن را نادیده بگیرد. متن alt جای caption یا عنوان طولانی نیست.
    • width/height — ابعاد intrinsic را مشخص کن تا مرورگر بتواند فضای مناسب رزرو کند و layout کمتر جابه‌جا شود. CSS هنوز می‌تواند اندازه نهایی را کنترل کند.
    • srcset/sizes — srcset چند candidate فراهم می‌کند؛ sizes به مرورگر تخمین می‌زند تصویر در layout چه عرضی دارد. این سیستم فقط «نسخه موبایل/دسکتاپ» ساده نیست.
    • picture — برای art direction مثل crop متفاوت یا formatهای جایگزین استفاده می‌شود. fallback img را نگه دار.
    • figure/figcaption — وقتی تصویر یک واحد مستقل با caption است، figure معنای رابطه را بهتر از div بیان می‌کند.
    • loading/decoding — lazy loading برای تصاویر خارج از viewport می‌تواند مفید باشد؛ تصویر اصلی بالای صفحه را کورکورانه lazy نکن. decoding="async" یک hint است، نه تضمین زمان رندر.

  </picture>
  <figcaption>تصویر معرفی پروژه.</figcaption>
</figure>

    ۴. اشتباهات رایج

    • نوشتن alt مثل «image.jpg» یا حذف alt بدون دلیل.
    • استفاده از width/height غلط که نسبت تصویر را خراب می‌کند.
    • استفاده از srcset بدون فهم sizes.
    • استفاده از picture برای کاری که CSS یا srcset کافی است.
    • lazy کردن همه تصاویر حتی تصویر LCP بالای صفحه.

    ۵. نکات طلایی حرفه‌ای

    • alt را با هدف تصویر بنویس، نه فهرست جزئیات غیرضروری.
    • width و height را با نسبت واقعی منبع هماهنگ کن.
    • برای hero image استراتژی loading را آگاهانه انتخاب کن.
    • فرمت‌های مدرن را در صورت نیاز با fallback مناسب عرضه کن.
    • در موبایل اندازه فایل مهم است؛ resolution بیش از نیاز کاربر هزینه دارد.

    • این معیار CLS را در Core Web Vitals بهبود می‌دهد.
    • در CSS با aspect-ratio هم می‌توانی نسبت را تعیین کنی.
    • با object-fit: cover تصویر بدون کشیدگی پر می‌شود.

    • srcset فهرست نسخه‌ها را با عرض واقعی (w) یا چگالی (x) می‌دهد.
    • sizes به مرورگر می‌گوید هر نسخه چقدر از صفحه را می‌گیرد.
    • با x برای صفحه‌های Retina مثل [email protected] 2x کار می‌کنی.
    • همیشه یک src پشتیبان داخل img بگذار.
    figure و picture چیست؟ ظرف و سوییچ تصویر
    • figure ظرف مستقل تصویر/دیاگرام + figcaption است.
    • picture برای انتخاب نوع فایل (AVIF/WebP/JPG) یا آرت‌دایرکشن است.
    • در picture هم img نهایی الزامی است؛ مرورگرهای ناسازگار آن را نمایش می‌دهند.
    • برای تصویر تزئینی صرف، figure لازم نیست.

    فرم‌ها: form، label، input و کنترل‌ها

    فرم را از label و name شروع می‌کنیم و به inputها، validation، autocomplete، fieldset و ارسال واقعی داده می‌رسیم.

    خروجی یادگیری فرم: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
    تمرین کوتاه فرم تماس را با label، name، type، required، autocomplete، fieldset و پیام خطای قابل فهم طراحی کن.
    قاعدهٔ طلایی هم اعتبارسنجی مرورگر را تست کن و هم نقش سرور را توضیح بده.
    📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

    ۱. مفهوم را دقیق بفهم

    form مجموعه کنترل‌هایی است که می‌تواند داده را submit کند. label نام قابل‌فهم کنترل را فراهم می‌کند. name کلید مهم داده ارسالی است. type رفتار و constraintهای کنترل را تعیین می‌کند. HTML validation با required/min/max/minlength/pattern/type و موارد دیگر می‌تواند خطاهای ساده را قبل از ارسال نشان دهد، اما اعتبارسنجی سرور همچنان لازم است.

    چرا مهم است؟

    فرم جایی است که semantics، accessibility، امنیت، UX و داده واقعی به هم می‌رسند. placeholder هرگز جای label نیست و validation مرورگر جای validation سرور نیست.

    ۲. ریزه‌کاری‌های این کورس

    • label/id — رابطه صریح for + id یکی از الگوهای واضح است؛ nesting label هم ممکن است. label باید واقعاً کنترل را توصیف کند.
    • name/value — کنترلی که name ندارد معمولاً در form data کلید قابل اتکا ندارد. مقدار submit شده بسته به type و state کنترل متفاوت است.
    • input types — email، url، tel، number، date، time، checkbox، radio، file، search، password و ... semantics و UI متفاوت دارند. نوع را بر اساس داده انتخاب کن.
    • validation — required، minlength، maxlength، min، max، step، pattern و type constraints هستند. پیام مرورگر را بشناس، اما برای خطاهای business logic به server اعتماد کن.
    • autocomplete/inputmode — autocomplete برای autofill درست و privacy-friendly مفید است. inputmode فقط hint برای نوع کیبورد است و validation انجام نمی‌دهد.
    • fieldset/legend — گروه‌بندی کنترل‌های مرتبط، مخصوصاً radio/checkboxها، با fieldset/legend معنا و تجربه بهتری می‌دهد.
    • button — در form، button به‌طور پیش‌فرض ممکن است submit باشد؛ type را آگاهانه submit ، button یا reset تعیین کن.

    ۳. مثال کامل قابل اجرا

    این مثال را می‌توانی مستقیم در یک فایل HTML قرار بدهی و نتیجه را در مرورگر ببینی. 

    <form action="/contact" method="post">
  <fieldset>
    <legend>اطلاعات تماس</legend>
    <label for="email">ایمیل</label>
    <input id="email" name="email" type="email" autocomplete="email" required>
    <label for="phone">تلفن</label>
    <input id="phone" name="phone" type="tel" inputmode="tel" autocomplete="tel">
    <label for="message">پیام</label>
    <textarea id="message" name="message" minlength="10" required></textarea>
  </fieldset>
  <button type="submit">ارسال</button>
</form>

    ۴. اشتباهات رایج

    • placeholder به جای label.
    • کنترل بدون name در فرم قابل ارسال.
    • خاموش کردن validation با novalidate بدون اینکه validation جایگزین داشته باشی.
    • اعتماد کامل به validation سمت مرورگر برای امنیت.
    • استفاده از input type=number برای هر چیزی که شبیه عدد است؛ شماره تلفن نمونه خوبی است که معمولاً number نیست.

    ۵. نکات طلایی حرفه‌ای

    • اول label و name را درست کن، بعد ظاهر را طراحی کن.
    • type را بر اساس semantics و تجربه دستگاه انتخاب کن.
    • خطا را کنار کنترل و با متن قابل فهم نشان بده.
    • اعتبارسنجی client-side برای UX است؛ server-side برای اعتماد و امنیت لازم است.
    • autocomplete درست، فرم را روی موبایل بسیار سریع‌تر می‌کند.

    ۶. تمرین

    یک فرم تماس کامل با نام، ایمیل، تلفن، موضوع، پیام، رضایت‌نامه checkbox و دکمه ارسال بساز و برای هر کنترل label، name و validation مناسب قرار بده.

    همهٔ مقادیر type=input از text تا color

    • date, time, datetime-local, month, week برای زمان و تاریخ.
    • checkbox, radio, range, color, file, hidden, search, submit, reset, button, image .

    label را چطور وصل کنم؟ دو راه درست

    • placeholder جای label نیست؛ با تایپ محو می‌شود و کنتراست ضعیفی دارد.
    • برای گروه رادیو/چک‌باکس، fieldset + legend زمینهٔ گروه را می‌سازد.

    • pattern الگوی regex را بررسی می‌کند، مثل کد ملی یا شمارهٔ تلفن.

    خروجی یادگیری رسانه: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.

    ۱. مفهوم را دقیق بفهم

    audio و video media playerهای native هستند. source اجازه می‌دهد چند منبع ارائه کنی. track برای timed text مثل captions/subtitles است. iframe سند دیگری را embed می‌کند و sandbox، loading و policyهای امنیتی/حریم خصوصی آن مهم‌اند. embed و عناصر embedded دیگر کاربردهای محدودتر و وابسته به نوع محتوا دارند.

    چرا مهم است؟

    media فقط قرار دادن URL نیست؛ باید کنترل، دسترس‌پذیری، captions، حجم، autoplay policy و fallback را در نظر بگیری.

    ۲. ریزه‌کاری‌های این کورس

    • audio/video — controls را برای کنترل native در سناریوهای معمول فعال کن. autoplay معمولاً محدودیت دارد و برای UX/دسترس‌پذیری باید آگاهانه استفاده شود.
    • source — چند source با type مناسب به browser امکان انتخاب فرمت سازگار می‌دهد. یک fallback متنی هم می‌تواند مفید باشد.
    • track — caption برای گفتار و صداهای مهم accessibility را بهتر می‌کند. زبان و kind را درست تعیین کن.
    • iframe — iframe محتوای یک browsing context جداست. title برای accessibility مفید است و sandbox می‌تواند قابلیت‌ها را محدود کند. برای embedهای شخص ثالث origin و privacy را هم بررسی کن.
    • loading — برای iframeهای پایین صفحه lazy loading می‌تواند بار اولیه را کاهش دهد.
    • picture در این کورس — picture تصویر است نه media player؛ اگر در درس کنار media استفاده می‌شود، آن را با هدف انتخاب تصویر/فرمت توضیح بده.

    ساختار معنایی: header، nav، main، section، article، aside، footer

    ساختار معنایی صفحه را با landmarkهای واقعی می‌سازیم تا HTML فقط یک ظاهر نباشد، بلکه نقشه‌ای از محتوا باشد.

    خروجی یادگیری ساختار: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
    تمرین کوتاه نقشهٔ یک صفحهٔ پرتفولیو را با header، nav، main، section، article، aside و footer روی کاغذ رسم و سپس پیاده کن.
    قاعدهٔ طلایی برای هر landmark دلیل معنایی داشته باش.
    📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

    ۱. مفهوم را دقیق بفهم

    header ، nav ، main ، section ، article ، aside و footer نقش‌های متفاوت دارند. main محتوای غالب document است؛ nav بخش navigation؛ section یک بخش مستقل که معمولاً heading دارد؛ article محتوای مستقل و قابل توزیع مجدد؛ aside محتوای جانبی مرتبط؛ header/footer مقدمه و پایان بخش یا document.

    چرا مهم است؟

    Semantic HTML ساختار را برای انسان و ماشین روشن می‌کند و می‌تواند دسترسی به landmarkها و navigation صفحه را بهتر کند.

    ۲. ریزه‌کاری‌های این کورس

    • main — در یک document معمولاً یک main اصلی داریم. محتوای تکرارشونده مثل nav و footer را داخل main نگذار مگر واقعاً محتوای اصلی همان بخش باشند.
    • nav — هر nav باید مجموعه navigation links معناداری داشته باشد. اگر چند nav داری، labelهای متمایز می‌توانند کمک کنند.
    • section — section جای div زیباتر نیست؛ وقتی موضوع/بخش مستقل داری و heading برای آن معنا دارد، section مناسب است.
    • article — برای محتوایی که به‌تنهایی هم قابل درک است، مثل پست، خبر، review یا کارت مقاله، article مناسب است.
    • aside — محتوای مرتبط ولی فرعی مثل sidebar، related links یا callout. صرفاً هر چیزی که کنار صفحه قرار گرفته aside نیست.
    • header/footer — می‌توانند متعلق به document یا یک section/article باشند و فقط یک بار در کل صفحه محدود نیستند.
    • div — div وقتی هیچ semantic element مناسبی وجود ندارد، همچنان کاملاً معتبر و مفید است.

    ۳. مثال کامل قابل اجرا

    این مثال را می‌توانی مستقیم در یک فایل HTML قرار بدهی و نتیجه را در مرورگر ببینی. 

    <header>...برند و معرفی...</header>
<nav aria-label="اصلی">...لینک‌ها...</nav>
<main>
  <article>
    <header><h1>عنوان مقاله</h1></header>
    <section><h2>بخش اول</h2><p>...</p></section>
    <footer>نویسنده و تاریخ</footer>
  </article>
  <aside aria-label="مطالب مرتبط">...</aside>
</main>
<footer>حقوق و لینک‌های کمکی</footer>

    ۴. اشتباهات رایج

    • استفاده از section فقط برای margin/padding.
    • قرار دادن همه چیز داخل div بدون معنا.
    • داشتن چند main برای یک document معمولی.
    • استفاده از article برای هر box تزئینی.
    • ساخت navigation با div و click handler.

    ۵. نکات طلایی حرفه‌ای

    • اول outline ذهنی محتوا را بکش، بعد tags را انتخاب کن.
    • heading باید با section/article انتخاب‌شده هماهنگ باشد.
    • landmarkها را بیش از حد تکرار نکن.
    • اگر عنصر معنایی خاصی نداری، div انتخاب سالمی است.
    • semantic HTML جای CSS نیست؛ هر دو نقش خودشان را دارند.

    ۶. تمرین

    ساختار یک صفحه مقاله را فقط با header/nav/main/article/section/aside/footer طراحی کن و کنار هر عنصر یک دلیل یک‌خطی بنویس.

    عناصر تعاملی و پویای بومی

    در این درس قابلیت‌های native برای disclosure، dialog، popover، progress، meter و output را از شبیه‌سازی‌های JavaScript جدا می‌کنیم.

    خروجی یادگیری تعامل بومی: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
    تمرین کوتاه یک FAQ با details، یک dialog و یک popover بساز و تفاوتشان را توضیح بده.
    قاعدهٔ طلایی اول قابلیت native را امتحان کن، بعد سراغ JavaScript برو.
    📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

    ۱. مفهوم را دقیق بفهم

    details/summary برای disclosure ساده، dialog برای dialog، popover برای محتوای popover، progress برای پیشرفت یک task، meter برای مقدار در یک range شناخته‌شده، و output برای نمایش نتیجه محاسبه/تعامل مناسب‌اند. native بودن یعنی بخشی از رفتار و semantics را browser مدیریت می‌کند؛ نه اینکه JavaScript هیچ‌وقت لازم نباشد.

    چرا مهم است؟

    وقتی قابلیت native دقیقاً با نیازت جور است، از ساختن نسخه جعلی با div، ARIA و چندین event handler پرهیز می‌کنی و رفتار پایه را به پلتفرم می‌سپاری.

    ۲. ریزه‌کاری‌های این کورس

    • details/summary — summary کنترل disclosure است و با open state والد details را تغییر می‌دهد. برای FAQ و محتوای قابل باز/بسته شدن ساده عالی است.
    • dialog — modal با showModal() و non-modal با show() باز می‌شود. برای هر dialog باید مسیر بستن مناسب و focus منطقی در نظر بگیری. dialog جای tooltip یا context menu نیست.
    • popover — popover یک primitive native برای محتوای موقت روی صفحه است. popovertarget و popovertargetaction امکان کنترل declarative دارند. پشتیبانی فعلی گسترده است اما سناریوهای خاص را روی browserهای هدف تست کن.
    • progress vs meter — progress می‌گوید یک کار چقدر پیش رفته؛ meter مقدار اندازه‌گیری‌شده در یک بازه است، مثل امتیاز یا ظرفیت.
    • output — برای نمایش نتیجه یک محاسبه یا action در form مناسب است و می‌تواند با for ارتباط منطقی با controls داشته باشد.
    • button — برای actionهای UI از button استفاده کن؛ اگر action باید navigation باشد، a مناسب‌تر است.

    • popover را بدون درک focus، dismiss و semantics در UI پیچیده به‌کار بردن.

    ۵. نکات طلایی حرفه‌ای

    • اول native primitive را امتحان کن، بعد JS اضافه کن.

    اسکریپت، template، slot و دادهٔ ماشین‌خوان

    HTML فقط محتوای ثابت نیست؛ script، template، slot و data/time به اتصال markup با رفتار و داده کمک می‌کنند.

    خروجی یادگیری داده و component: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
    تمرین کوتاه یک کارت پروژه را با template آماده کن و تاریخ/قیمت را با time و data ماشین‌خوان کن.
    قاعدهٔ طلایی slot را فقط در سناریوی Web Component و Shadow DOM به‌کار ببر.
    📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

    ۱. مفهوم را دقیق بفهم

    script برای کد یا reference به script است؛ template markup غیرفعال و قابل clone را نگه می‌دارد؛ slot جایگاه محتوا در Web Components/Shadow DOM است؛ data متن قابل مشاهده را با مقدار machine-readable پیوند می‌دهد؛ time تاریخ/زمان را machine-readable می‌کند؛ noscript fallback برای شرایطی است که script اجرا نمی‌شود.

    چرا مهم است؟

    این عناصر مرز بین markup و runtime را روشن می‌کنند. استفاده نادرست از template/slot یا قرار دادن داده حساس در HTML می‌تواند طراحی را پیچیده یا ناامن کند.

    ۲. ریزه‌کاری‌های این کورس

    • script — defer برای script کلاسیک خارجی معمولاً بعد از parse و قبل از DOMContentLoaded اجرا می‌شود؛ async مستقل است و ترتیب را تضمین نمی‌کند؛ moduleها deferred-like هستند و scope متفاوت دارند.
    • template — محتوای template هنگام parse صفحه مثل محتوای عادی render نمی‌شود؛ با content.cloneNode(true) یا روش‌های مرتبط می‌توان آن را instantiate کرد. داده کاربر را بدون escaping داخل HTML template نکن.
    • slot — slot در Shadow DOM برای projection محتواست و بیرون از Web Components معنای کاربردی مشابه یک placeholder عمومی ندارد.
    • data/time — data برای مقدار machine-readable کنار متن قابل مشاهده است؛ time برای زمان/تاریخ semantics مشخص‌تری دارد.
    • microdata/JSON-LD — اگر structured data لازم است، JSON-LD اغلب از نظر نگهداری ساده‌تر است؛ اما نوع داده و دستورالعمل مصرف‌کننده را باید بررسی کرد.
    • noscript — fallback است، نه راهی برای «اجباری کردن» JavaScript. صفحه باید تا حد امکان بدون وابستگی بی‌دلیل به script قابل فهم بماند.

    ۳. مثال کامل قابل اجرا

    این مثال را می‌توانی مستقیم در یک فایل HTML قرار بدهی و نتیجه را در مرورگر ببینی. 

    <template id="card-template">
  <article class="card">
    <h2></h2>
    <p></p>
  </article>
</template>

<time datetime="2026-09-23">۲۳ سپتامبر ۲۰۲۶</time>
<data value="sku-42">محصول شماره ۴۲</data>

<script defer src="app.js"></script>
<noscript>برای این صفحه JavaScript فعال نیست.</noscript>

    ۴. اشتباهات رایج

    • استفاده از async وقتی ترتیب اجرای چند script مهم است.
    • تصور اینکه template خودش render می‌شود.
    • استفاده از slot بدون Shadow DOM/Web Components.
    • قرار دادن داده حساس در data یا HTML با این تصور که مخفی است.
    • نوشتن fallback noscript که کل تجربه را غیرقابل استفاده می‌کند.

    ۵. نکات طلایی حرفه‌ای

    • script strategy را بر اساس dependency انتخاب کن.
    • template را برای markup قابل تکرار و runtime instantiation نگه دار.
    • slot را همراه مدل Shadow DOM یاد بگیر.
    • machine-readable بودن به معنی secret بودن نیست.
    • برای structured data مصرف‌کننده و schema دقیق را بررسی کن.

    ۶. تمرین

    یک template کارت بساز و با JavaScript آن را سه بار clone کن؛ سپس برای قیمت/شناسه از data و برای تاریخ انتشار از time استفاده کن.

    مرجع جامع عناصر HTML Living Standard

    در پایان، عناصر HTML را بر اساس خانواده می‌شناسیم، موارد obsolete را جدا می‌کنیم و از روی reference تصمیم می‌گیریم چه عنصری واقعاً مناسب است.

    خروجی یادگیری جمع‌بندی: مفهوم را می‌فهمی و در پروژه به‌کار می‌بری.
    تمرین کوتاه پرتفولیوی نهایی را بدون نگاه به درس‌نامه از صفر بساز و سپس با validator و DevTools بررسی کن.
    قاعدهٔ طلایی هر خطایی که پیدا کردی را با علتش توضیح بده، نه فقط با حذف خط.
    📱 روی موبایل: کدها را افقی اسکرول کن؛ ساختار درس عمداً تک‌ستونه می‌شود تا متن و مثال خوانا بمانند.

    ۱. مفهوم را دقیق بفهم

    HTML Living Standard تعداد زیادی عنصر را در خانواده‌های metadata، sectioning، text، inline semantics، media، embedded، table، form، interactive و Web Components تعریف می‌کند. مهم‌تر از حفظ فهرست، شناخت content model، attributes، semantics و nesting rules هر عنصر است.

    چرا مهم است؟

    یک توسعه‌دهنده خوب لازم نیست صدها تگ را از حفظ بنویسد؛ باید بتواند از reference عنصر مناسب را پیدا کند، محدودیت‌های nesting را بفهمد و انتخابش را بر اساس معنا انجام دهد.

    ۲. ریزه‌کاری‌های این کورس

    • Global attributes — id، class، lang، dir، hidden، title، data-*، tabindex و بسیاری دیگر در سطح عمومی مطرح‌اند؛ اما «global» به معنی بی‌قید بودن رفتارشان روی همه عناصر نیست.
    • Void elements — عناصری مثل img، input، br، hr، meta، link، source، track و area محتوای فرزند ندارند و closing tag ندارند.
    • Content models — هر عنصر می‌تواند مدل محتوای خاصی داشته باشد؛ مثلاً چیزی که داخل button مجاز است لزوماً داخل p یا a مجاز نیست. این قواعد جلوی markup نامعتبر یا رفتار parser عجیب را می‌گیرند.
    • Obsolete elements — عناصر قدیمی مثل font، center، marquee و ... را در پروژه جدید استفاده نکن؛ ظاهر باید با CSS و semantics با عناصر مدرن ساخته شود.
    • Reference-first workflow — وقتی درباره یک عنصر شک داری، MDN برای توضیح عملی و WHATWG برای استاندارد مرجع مناسبی هستند. compatibility و وضعیت browser را جداگانه بررسی کن.
    • Parser behavior — مرورگر HTML را tolerant parse می‌کند و ممکن است markup ناقص را اصلاح کند؛ «در مرورگر نمایش داده شد» به معنی valid و maintainable بودن کد نیست.

    • نادیده گرفتن content model و nesting rules.
    • اعتماد به اینکه browser parser هر markup اشتباهی را به همان چیزی که قصد داشتی تبدیل می‌کند.

    ۵. نکات طلایی حرفه‌ای

    • برای انتخاب عنصر از سؤال «معنای این محتوا چیست؟» شروع کن.
    • اگر بین دو عنصر شک داری، reference و content model را بخوان.
    • HTML semantic را با CSS presentational قاطی نکن.
    • obsolete بودن را با «کار کردن در browser» اشتباه نگیر.
    • یک reference کوچک شخصی بساز، اما هنگام پروژه به مستندات زنده رجوع کن.

    فلش‌کارت — ریزنکات این بخش

    void element چیست؟ تگ بدون closing tag
    • عناصر void محتوای فرزند ندارند: area، base، br، col، embed، hr، img، input، link، meta، source، track، wbr.
    • نوشتن <img></img> غلط/بی‌اثر است؛ همان <img ...> کافی است.
    • اسلش پایانی در HTML مثل <br /> الزامی نیست؛ فرم HTML را با XML قاطی نکن.
    • meta، link و input هم void هستند.
    Global attributes کدام‌اند؟ ویژگی‌هایی که تقریباً همه‌جا می‌آیند
    • id، class، style، title، lang، dir، hidden، inert، tabindex، data-*، contenteditable، draggable، spellcheck، translate.
    • role، aria-* و slot/is برای سناریوهای ویژه‌اند؛ ARIA را جای semantic HTML نگذار.
    • accesskey را با احتیاط استفاده کن چون با میانبرهای سیستم و صفحه‌خوان تداخل دارد.
    • id یکتا، class برای گروه، data-* برای دادهٔ سفارشی DOM است.
    عناصر obsolete را بشناسم؟ یادگیری برای تشخیص کد قدیمی
    • center، font، big، strike، tt، marquee، frame، frameset، noframes، acronym، dir و keygen را استفاده نکن.
    • ظاهر آن‌ها با CSS و ساختار آن‌ها با تگ معنایی جدید جایگزین می‌شود.
    • bgsound، blink، plaintext و xmp نیز legacy/obsolete هستند.
    • در مستندات ممکن است برای مهاجرت ببینی‌شان، نه برای ساخت پروژهٔ جدید.
    HTML parser چرا مهم است؟ DOM واقعی همیشه عین متن نیست
    • مرورگر تگ‌های ناقص یا nesting نامعتبر را اصلاح می‌کند و ممکن است درخت DOM دیگری بسازد.
    • مثلاً قرار دادن block داخل p باعث بسته‌شدن ضمنی p می‌شود.
    • برای اشکال‌زدایی، Elements panel را با source متن یکی فرض نکن.
    • اعتبارسنجی با Nu HTML Checker یا ابزارهای lint کمک می‌کند.

    چک‌لیست دقیق پروژه

    قبل از اینکه بگویی تمرین تمام شده، این موارد را دستی آزمایش کن.

    • DOCTYPE، lang="fa"، dir="rtl" و UTF-8 درست هستند.
    • title، description، canonical و viewport نوشته شده‌اند.
    • یک h1، headingهای مرتب و sectionهای دارای عنوان دارم.
    • header/nav/main/footer و landmarkهای واقعی استفاده شده‌اند.
    • لینک‌های داخلی به id یکتا می‌رسند و متن لینک واضح است.
    • تصویر width/height و alt دارد؛ تصویر تزئینی alt خالی دارد.
    • جدول caption، thead/tbody/tfoot، th و scope دارد.
    • هر کنترل فرم label، name و type درست دارد.
    • فرم هم اعتبارسنجی HTML دارد هم قرار است سمت سرور بررسی شود.
    • صوت و ویدیو controls، fallback و track مناسب دارند.
    • با Tab، Enter و Space کل تعاملات کار می‌کنند.
    • focus دیده می‌شود و رنگ تنها راه اعلام وضعیت نیست.
    • انیمیشن در prefers-reduced-motion کاهش می‌یابد.
    • تگ‌های منسوخ مثل center، font، marquee و frame استفاده نشده‌اند.
    تمرین عملی نهایی: همین درس‌نامه را کنار بگذار و پرتفولیوی خودت را از صفر بساز. بعد با HTML validator، DevTools و Lighthouse آن را بررسی کن. فرق «دیدن کد» و «توانستن ساختن» همین‌جاست.
